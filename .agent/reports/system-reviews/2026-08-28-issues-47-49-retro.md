# Retrospective — 2026-08-28 — Review Flow and Provider Dashboard

## Scope and outcome

This session completed two design-parity repair slices:

- Issue [#47](https://github.com/MarkoAtc/QuickWerk/issues/47) shipped in PR [#48](https://github.com/MarkoAtc/QuickWerk/pull/48): the completed-booking review route now uses real booking/provider data, handles invalid states safely, and matches `design/review_rating`.
- Issue [#49](https://github.com/MarkoAtc/QuickWerk/issues/49) shipped in PR [#50](https://github.com/MarkoAtc/QuickWerk/pull/50): the provider dashboard now loads authoritative requests, supports safe accept/decline transitions, and matches the core `design/provider_dashboard` experience.

Both PRs are merged. PR #50 passed the pull-request validation gate, manual CodeRabbit review with no actionable findings, and the post-merge `main` CI run.

## What worked well

1. **Narrow, issue-first slices kept behavior and design work reviewable.** Each slice had a dedicated plan, explicit acceptance criteria, and real-data boundaries. Unsupported metrics or capabilities were not fabricated to fill the mockups.
2. **The validation ladder found different classes of defects.** Focused tests established the request contracts; workspace typechecking caught cross-package TypeScript problems; full suites and builds proved integration; Expo export caught route/import risks; live browser QA proved the actual authenticated journeys.
3. **A fresh review before the PR materially improved #49.** It caught and drove fixes for strict transition-response binding, a refresh/action race, accessibility announcements, and safe-area handling before external review.
4. **The PR review loop was completed rather than treating PR creation as done.** CodeRabbit was manually requested after its automatic review was skipped, the CI state was monitored, and the loop ended only after no actionable feedback remained.
5. **Scope discipline held.** Authentication, payment, and privacy contracts were not changed as incidental parts of the UI repairs.

## What slowed the work down

1. **The repository's ADOS contract is incomplete.** `.agent/rules/00-core.md` is referenced by workflows but absent. The expected `retro`, `system-review`, `execution-report`, `code-review`, and `context-checkpoint` workflows are also absent, requiring documented fallbacks.
2. **Validation instructions have drifted.** `AGENTS.md` names root `pnpm test:run` and `pnpm build` commands that do not exist. The effective validation contract is currently `.github/workflows/ci.yml` plus Expo export and live-flow checks where relevant.
3. **The CodeRabbit workflow assumes automatic review.** This repository's automatic review was skipped because the public repository did not meet CodeRabbit's current eligibility threshold. A manual `@coderabbitai review` request was necessary, but `.agent/workflows/review-pr.md` does not describe that branch.
4. **Local browser QA needs an API-base override.** `apps/product-app/.env` targets `localhost:3000`, while the normal local API path used during this work was port `3101`. The mismatch adds avoidable setup/debugging time.
5. **The provider-specific auth route opens with the customer role selected.** `/auth-provider` uses the generic `AuthEntryScreen`, whose initial role is customer, so a user arriving via “Continue as a provider” must select “I am a pro” again. This was out of scope for #49 but should be handled as a small follow-up.

## Improvements to carry forward

- Restore or formally replace `.agent/rules/00-core.md` and the missing referenced workflows.
- Align `AGENTS.md` validation commands with the actual root scripts/CI workflow.
- Add the manual-review fallback and skip-detection path to `.agent/workflows/review-pr.md`.
- Document one canonical local API port/base-URL setup for product-app browser verification.
- Preserve the fresh-review pass for stateful UI work; it provided more value than another broad reread of the same diff.

These are recommendations only; no workflow or environment files were changed during wrap-up.

## Follow-up issue draft

### Make the provider auth entry default to the provider role

**Problem:** `/auth-provider` is reached from “Continue as a provider” but renders the customer role as selected by default.

**Acceptance criteria:**

- `/auth-provider` initially selects the provider role and presents provider-oriented copy/actions.
- The generic customer authentication route keeps its current default.
- Sign-in and sign-up requests continue sending the explicitly selected role.
- Tests cover both route defaults and prevent a regression.
- Authentication policy and backend authorization behavior remain unchanged.

**Likely implementation seam:** add an explicit initial-role input to `AuthEntryScreen` and pass `provider` only from `apps/product-app/app/auth-provider.js`.
